# `dsh-lark` 流更新合并设计

[English](2026-08-26-dsh-lark-stream-coalescing-design.md) | 中文

**日期：** 2026-08-26

**状态：** 已确认进入实现

## 目标

保留现有飞书打字机卡片，同时避免模型分片变成串行积压的 `im.message.patch` 请求。Harness 轮次完成后，飞书最多只需等待一个已经在途的卡片请求；不得修改 Harness 核心、Desktop 会话存储或 Session 事件流。

## 根因

当前 `TurnCardStream.update()` 会把每个投影修订追加到同一条 promise 尾链。每个非最终条目都要等待 `streamThrottleMs`，默认值为 350 ms，而且 `onMuxFrame()` 会逐个等待这些条目。因此，包含 100 个分片的回答会产生 101 次卡片写入和约 35 秒的本地调度延迟，即使 Harness 已经完成该轮次也一样。

飞书传输使用 `im.message.patch`，其限流比 CardKit 流式接口更严格。单纯缩短间隔仍会为每个分片发送一次请求，只会增加限流风险，不能消除积压。

## 调度器

每个轮次仍只持有一张稳定卡片和一个 `TurnCardStream`。流控制器只保存最新的已准入 `TurnProjectionState`、dirty 标记、一个可选节流计时器和一个可选在途卡片请求。

非最终更新会替换最新状态，并且不等待网络写入就返回。如果当前没有请求或计时器，调度器会在节流窗口已经结束时立即写入，否则只为剩余间隔设置一个计时器。计时器触发前或请求在途期间收到的更新都会合并为最新状态。

最终更新会取消节流计时器。没有请求在途时，它立即写入最新最终状态；存在一个在途请求时，它先等待该请求，再立即写入一次最新最终状态。最终更新 promise 只会在这次排空完成后结算，因此终态卡片尚未完成时不会删除活动轮次记录。

卡片文字仍保持单调：文字缩短或不再匹配可见前缀的投影会被忽略。文字相同的修订仍然有效，因此工具状态、审批按钮、运行时事实、耗时和 token 用量可以独立更新。

## 失败与生命周期

第一次卡片更新失败后，该轮次不再写卡片，并从最新状态发送一次有界文本降级回复。后续修订不能再次发送降级回复。降级回复自身失败也不会终止共享 mux 循环。

`TurnCardStream.stop()` 会取消计时器并拒绝后续调度。插件停用时，先对所有活动流调用 `stop()`，再清空活动轮次映射，因此延迟中的飞书请求不会在插件关闭后继续发送。已经完成的 Harness Session 及其事件日志不受影响。

## 插件隔离

Lark 包继续通过已经公开的 `resolveOrdinaryTargetForSource()` API 和包内外部来源哨兵解析普通 Session。`@deepseek-ai/dsh-session-messenger` 中未被使用的 `assertOrdinarySession()`、`resolveOrdinarySession()` 以及对应测试会被移除。

必要的 monorepo 注册继续保留：包 manifest、TypeScript 聚合引用、锁文件条目、生成的 Client slot 注册、文档和可独立安装的 Bundle。`packages/core/agent`、`packages/core/session`、Desktop 应用包和 Desktop 默认 patch 下的文件都不会修改。

## 验证

聚焦测试使用确定性计时器和延迟结算的卡片请求，证明突发更新合并、节流间隔、最终状态优先、最多一个在途请求、文字单调、单次有界降级和停用取消。现有渲染测试继续固定模型 ID、提供方、推理档位、耗时、token 用量、缓存计数和审批操作。

包测试、类型检查、构建、文档同步、diff 检查、tarball 打包、真实 `web` Profile 安装、重启状态和已安装字节核对共同构成发布证据。真实飞书时延仍需要安装后由所有者发送一次私聊验证，因为离线测试无法测量飞书网络延迟。

## 已考虑的替代方案

**降低 `streamThrottleMs`。** 未采用，因为它仍会为每个分片发送一次 patch，并增加触发飞书错误 `230020` 的风险。

**只发送最终答案。** 未采用，因为这会移除用户要求的打字机进度以及工具和审批可见性。

**把流调度移入 Harness 核心。** 未采用，因为飞书调度属于可移除的传输插件，而且 Harness 已经发布全部所需 Session 事件。
