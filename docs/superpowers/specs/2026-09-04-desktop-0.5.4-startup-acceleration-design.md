# Desktop 0.5.4 Startup Acceleration Design

English | [中文](2026-09-04-desktop-0.5.4-startup-acceleration-design.zh.md)

**Status:** Approved by the user on 2026-09-04; implementation pending

**Desktop baseline:** `0da8093092c9a29f5cebdfc094d0b58d97b56219` (public `desktop-v0.5.3`)

**Harness core baseline:** `0.1.2-alpha.5`; target `0.1.2-rc.1`

**Target Desktop version:** `0.5.4`

## Goal

Reduce the time from application launch to the real interactive Desktop surface by optimizing the measured Loader critical path. Keep readiness, profile validation, authorization, upgrade recovery, and failure propagation unchanged.

## Measured baseline

The final 0.5.3 Windows same-runner evidence compared a pinned 0.5.1 installer with the 0.5.3 candidate using five cold and five warm samples per product.

| Metric | 0.5.1 | 0.5.3 | Result |
|---|---:|---:|---|
| Cold median | 4866ms | 6834ms | Regression to investigate |
| Cold P95 | 6389ms | 7455ms | Regression to investigate |
| Warm median | 3486ms | 5931ms | Regression to investigate |
| Warm P95 | 3535ms | 6185ms | Regression to investigate |
| 0.5.3 cold `profile-compose → loader-mount` | — | 2513ms | Main bounded child phase |
| 0.5.3 warm `profile-compose → loader-mount` | — | 2613ms | Main bounded child phase |

`loader-mount → loader-settle` is tens to low hundreds of milliseconds in those samples, while URL readiness is also short after the child reports its URL. The first optimization target is therefore work inside root include creation and activation, not an earlier readiness signal and not removal of the module-fallback safety checks.

These five-sample values identify the investigation target but do not constitute the 0.5.4 release benchmark. The release decision uses the larger sample contract below.

## Measurement contract

- Existing fixed Desktop milestones and child timing lines remain path-free, configuration-free, and credential-free.
- Add fixed internal marks that separate Loader construction, root-include start, first-party module resolution and import, root activation, settle, and activation audit.
- Detailed names are allowed only for an explicit first-party package allowlist. User-installed packages are reported only as aggregate count, total time, and maximum time, without package name, path, configuration, or arguments.
- Every duration is a non-negative safe integer. Unknown, malformed, duplicate, or impossible-order evidence fails closed as benchmark evidence but does not convert a healthy product launch into a product failure.
- Ordinary CLI launches emit no startup timing. Only the exact Desktop diagnostic environment enables the timing channel.
- Portable CI artifacts contain summaries and bounded allowlisted timing records, not lifecycle logs, CPU profiles, `DSH_HOME`, URLs, paths, prompts, environment values, or credentials.

## Optimization ladder

Implementation follows measured impact and stops at the first safe change that satisfies the release gate.

1. Remove redundant first-party file reads, YAML parsing, module resolution, or composition performed more than once on the same immutable inputs during one boot.
2. Move a measured noncritical first-party extension out of the startup critical path only when session restore, routing, authorization, Client manifest, first conversation render, and failure reporting do not depend on it.
3. If repeated immutable work remains dominant, add a rebuildable cache keyed by exact Desktop/core versions, platform, architecture, package lock, built-in profile, bundle, patch, and module-content digests.
4. On cache miss, corruption, version mismatch, digest mismatch, or unsupported input, recompute through the ordinary path. Never delete or rewrite the user's profile, patches, sessions, Memory/Evolution data, browser state, or credentials.

User-owned profile and overlay files remain read and validated on every launch. Physical module roots, package boundaries, upgrade recovery, and product errors continue to fail closed. The design does not serialize a live Cordis context, reuse active services across processes, parallelize side-effectful plugin activation without ordering proof, or skip a Loader generation.

## Readiness and user experience

- `dsh web:` remains emitted only by the real web runtime at its existing point.
- `harness-ready` continues to require the real readiness route and boot manifest.
- `desktop-running` continues to require the real Desktop surface, not the loading window.
- The loading window must remain visible promptly and responsive while the measured child path runs.
- BrowserSkill remains dormant until enabled or invoked and must not add a browser probe or daemon to cold start.

## Tests and evidence

1. Timing parser tests reject malformed, duplicate, unknown, and chain-inverted records while accepting legal interleaving of independent chains.
2. The selected optimization begins with a focused RED test that reproduces the redundant or unnecessarily eager work, then a minimal GREEN change.
3. Cache tests, if a cache is selected, cover exact hits plus version, lock, patch, bundle, module, platform, architecture, truncation, tampering, and foreign-file invalidation.
4. Correctness regression covers profile boot, Loader failure propagation, legacy fallback recovery, session restore, authorization, routing, BrowserSkill dormancy, and process-tree shutdown.
5. Each platform compares the pinned public 0.5.3 product with the same 0.5.4 final SHA on the same runner using ten cold and ten warm launches.
6. The report includes median and P95 for total startup and every fixed phase. It distinguishes improvement, regression, and ordinary run-to-run variance.

## Performance gate

- At least one of cold or warm total median improves by 15% or more.
- The other total median regresses by no more than 5%.
- Neither total P95 regresses by more than 10%.
- Correctness, readiness, native lifecycle, and user-data preservation gates stay fully green.
- If the product optimization misses any threshold, revert that optimization and retain only safe diagnostic improvements. Do not release an unproven fast path or claim that startup is faster.

## Ownership and delivery

The commander is the sole owner of shared timing and startup implementation. The Mac execution task owns Intel macOS baseline and candidate native measurements. The Windows execution task owns Windows x64 baseline and candidate native measurements. Platform tasks consume one shared commit and may change only their platform measurement or lifecycle harnesses.

The startup work lands after the independent left-rail correction. The final version bump, release metadata, tag, and public assets wait for one final SHA that passes both native platforms.

## Acceptance criteria

1. A phase-level report identifies the measured work removed or deferred and contains no private user data.
2. The same-machine ten-cold/ten-warm comparison satisfies the performance gate on Mac Intel and Windows x64.
3. Startup does not report URL, Harness readiness, or Desktop readiness earlier than the real corresponding state.
4. Existing profiles, sessions, Memory/Evolution data, authorization state, and BrowserSkill state remain intact through upgrade, launch, exit, and uninstall.
5. A failed or invalid cache, when present, falls back to the ordinary validated path without making the application unstartable.

## Rollback

Timing additions and the product optimization are separate commits. The optimization can be reverted while preserving diagnostic evidence. A cache, when present, is rebuildable and removable; rollback never touches user-owned data.
