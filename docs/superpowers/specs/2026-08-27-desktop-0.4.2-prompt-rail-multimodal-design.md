# Desktop 0.4.2 Prompt Rail and Custom Multimodal Model Design

English | [中文](2026-08-27-desktop-0.4.2-prompt-rail-multimodal-design.zh.md)

## Goal

Deliver Mac Intel and Windows x64 Desktop 0.4.2 from one source commit, based on the public 0.4.1 source. Add a Codex-style prompt navigation rail without adding rewind semantics, and let users accurately declare image input support for custom models.

## Scope and non-goals

- Preserve all 0.4.1 session data, plugins, settings, model routing, reasoning controls, and existing official branch behavior.
- Add a left transcript-gutter rail for completed user prompts and steering messages.
- Remove the 0.4.2 edit-from-prompt, before-turn fork, restored draft, and rollback entry points. The rail never creates a session, changes history, restores a draft, or sends a message.
- Add an input-capability control to custom `pi-ai` model entries: Automatic, Text only, or Text and images.
- Accept endpoint-discovered input modalities only when the endpoint returns explicit, recognized metadata. Model names and IDs are not capability evidence.
- Keep NewAPI-specific context-window discovery and unrelated provider changes outside this release.

## Prompt anchor data

The Host projects a lightweight all-history `promptAnchors` index from the same immutable session-event cut used by the initial history response. Each anchor contains the event sequence, a length-bounded normalized preview, and whether the event opened a turn or steered an active turn. Older history pages carry message bodies only because the initial index already covers every reachable prompt in that cut.

The Client stores anchors separately from rendered message groups. Clicking an anchor asks the existing history pager for older pages only until the target sequence is present, then scrolls the exact user message into view. A missing or compacted target produces a non-destructive unavailable state; it never falls back to a nearby message.

Anchor projection is navigation metadata only. It does not change session log formats, model-visible context, turn grouping, fork boundaries, or source-session contents.

## Prompt rail experience

The rail occupies a dedicated narrow gutter on the left side of the transcript and does not overlap or resize the message column. Turn-opening prompts use longer ticks, steering prompts use shorter ticks, and the anchor nearest the viewport center uses the DeepSeek theme color. The Client groups nearby anchors when necessary so long sessions keep a bounded number of rendered ticks while retaining the first and latest reachable areas and the exact anchor represented by each interactive tick.

Hover and keyboard focus show a styled preview popover with normalized, truncated prompt text. Click, Enter, and Space jump to the selected prompt. The active tick updates from transcript visibility, not from click state alone. Reduced-motion preferences disable animated scrolling, and narrow layouts hide the rail rather than covering content.

The rail has no edit, rewind, delete-later-content, child-session, draft restoration, or auto-send action. The new edit-from-prompt control introduced by the replaced 0.4.2 release is not part of this implementation.

## Custom model input capability

Each declared `pi-ai` model exposes an Input capability selector:

- Automatic: omit the model-level `input` field and inherit a trusted installed catalog entry or the route default.
- Text only: persist `input: ["text"]`.
- Text and images: persist `input: ["text", "image"]`.

The editor preserves unrelated and future model fields during edits. Existing configurations without `input` remain Automatic, so this change does not rewrite user model files or silently enable images.

Model discovery carries optional input modalities through the Host API. The provider parser recognizes explicit text and image modality metadata in supported top-level or provider architecture fields, normalizes recognized aliases, and ignores missing, empty, or unknown values. Adoption writes discovered modalities only when reliable metadata exists. It never infers vision support from substrings such as `vision`, `vl`, or a model vendor name.

The resolved model profile remains the authority for attachment admission. A custom model resolved with `image` accepts image attachments; a text-only model continues to reject them before a request is sent.

## Failure handling and compatibility

- History paging failures leave the conversation usable and show the selected anchor as unavailable.
- Duplicate, malformed, or out-of-order anchors are rejected or de-duplicated at the wire and Client boundaries.
- Unknown discovery metadata does not broaden model permissions.
- The release does not read, print, migrate, or package provider credentials.
- No operation deletes or rewrites `~/.dsh`, Desktop user data, sessions, memory databases, or installed external plugins.
- Mac and Windows packages use the same source commit. Unsigned or unnotarized boundaries remain explicit unless the release environment already supplies signing credentials.

## Verification

- Host tests cover recent and paged prompt-anchor projection, steering classification, normalization, ordering, de-duplication, and long histories.
- Client and UI tests cover bounded rendering, first and latest reachability, active tick updates, hover and keyboard previews, exact paging and scrolling, unavailable targets, narrow layouts, and reduced motion.
- Regression tests prove rail actions do not call edit, fork, draft restore, send, delete, or mutate-history paths.
- Model configuration tests cover Automatic, Text only, Text and images, catalog inheritance, route-default fallback, and preservation of unrelated fields.
- Discovery and wire tests cover supported explicit metadata, aliases, empty and unknown metadata, and adoption round trips.
- Attachment tests prove that declared image-capable custom models accept images while text-only custom models reject them.
- Keyless product snapshots, focused unit tests, typecheck, lint, build, and documentation checks pass before packaging.
- Mac DMG packaged smoke and `hdiutil verify` pass. Windows Setup completes native visible install, launch, close, uninstall, shortcut cleanup, and Harness data-preservation verification from the same commit.
- Local Mac replacement backs up the installed 0.4.1 application, preserves `~/.dsh`, installs the verified 0.4.2 application, and verifies the bundle version, architecture, Harness readiness, and preserved data before removing the backup.

## Release replacement

The already-published `desktop-v0.4.2` release is replaced only after the corrected source is merged and both native artifacts pass verification. The exact existing Release and tag are resolved again immediately before deletion. The replacement tag points to the final shared source commit, and public assets are verified by uploaded state, exact size, SHA-256, checksum-file validation, and one anonymous download per platform.

Reusing 0.4.2 has a compatibility cost: clients that already installed the earlier 0.4.2 may not detect an equal-version replacement, and intermediary caches may briefly serve old bytes. Release notes must disclose this boundary and provide checksum-based manual replacement instructions. The local 0.4.1 installation can update normally because 0.4.2 is a higher version.
