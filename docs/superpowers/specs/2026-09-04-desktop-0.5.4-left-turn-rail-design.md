# Desktop 0.5.4 Left Turn Rail Design

English | [中文](2026-09-04-desktop-0.5.4-left-turn-rail-design.zh.md)

**Status:** Approved by the user on 2026-09-04; implementation pending

**Desktop baseline:** `0da8093092c9a29f5cebdfc094d0b58d97b56219` (public `desktop-v0.5.3`)

**Harness core baseline:** `0.1.2-alpha.5`

**Target Desktop version:** `0.5.4`

## Goal

Place the Turn navigation rail in the conversation body's left gutter, keep it visually separate from transcript text, and preserve the existing complete-history, keyboard, preview, and composer-avoidance behavior.

## Confirmed problem

The approved 0.5.3 design places Turn navigation in the left gutter, but the released stylesheet describes and anchors the rail in the right gutter with `right`. The preview consequently opens toward the transcript from the right edge. This is an implementation mismatch, not a new preference or a data-model defect.

The existing first-party `TurnNavigator`, `turnOutline`, `loadThrough`, and active-Turn state remain the only navigation truth. This work changes placement and collision behavior only.

## Visual contract

- The rail occupies the conversation's start-side gutter, which is the left gutter in the supported Chinese and English layouts.
- The resting track stays outside the transcript text column with a visible 12–16px separation. It must not change message width, indentation, or wrapping.
- Marks share one left origin and extend toward the transcript. Resting, preview, busy, unloaded, active, and keyboard-focus states keep their existing semantics.
- The preview opens to the right of the rail as a floating layer. It never participates in document flow, never changes transcript geometry, and uses a 10–12px gap from the track.
- The preview remains at most 300px wide, shows one prompt line and at most three response lines, and uses the existing bounded conversation band for vertical clamping.
- The preview may cover transcript content transiently while the user hovers or focuses a mark, but it must never enter the composer, QueueDock, statistics row, or right Workbench.
- The zero-height sticky slot remains zero-height, so the rail and preview add no transcript scroll height.
- Fewer than two Turns render no rail. Long histories scroll inside the rail, and the active mark remains visible unless the pointer is controlling the rail.
- The rail remains visible in the default 1012px Desktop window while the sidebar is expanded and the Workbench is closed. It hides only when the center conversation column is narrower than 680px, preventing collisions with the transcript, composer, or an open Workbench.

## Interaction and accessibility

- Pointer movement previews the nearest mark and click navigation uses the same fixed-pitch mapping.
- Each Turn remains a keyboard-focusable button with the existing localized accessible name, `aria-current`, `aria-busy`, and tooltip relationship.
- Reduced-motion mode disables rail and preview animation without changing navigation.
- Light and dark themes use existing design tokens; no fixed black, white, or platform-only color becomes the source of state.

## Implementation boundaries

- Prefer CSS logical positioning for the conversation start side, with a documented left-side result for the supported locales.
- Keep `TurnNavigator.tsx`, the Turn outline model, pagination, and navigation callback unchanged unless a failing test proves a placement-specific defect.
- Do not add another rail, import `dsh-session-nav`, or target generated CSS-module class names from Desktop code.
- Do not reserve a permanent preview-width column or move the transcript to make room for a transient preview.
- Do not change BrowserSkill, approval behavior, session grouping, or the composer data flow in this track. Workbench docking thresholds and trigger polish belong to the separate 0.5.4 interface specification.

## Tests and evidence

1. A focused stylesheet contract fails while the rail is right-anchored and passes only when the track is start-side anchored and the preview opens toward the transcript.
2. Component tests retain complete-history, unloaded-page navigation, active-state, keyboard, long-history scrolling, and reduced-motion behavior.
3. Browser layout tests at 100%, 150%, and 200% verify that the rail is left of the first transcript content, remains visible in the default 1012px window, and does not change transcript dimensions when a preview opens.
4. Tests with short, long, Chinese, and English content verify that the preview remains outside the measured composer band and does not intersect the right Workbench.
5. Mac Intel and Windows x64 native evidence captures the rail, two or more marks, one active mark, and an open preview at their platform scale factors.

## Ownership and delivery

The commander is the sole owner of the shared Turn rail implementation and its cross-platform tests. The Mac and Windows execution tasks consume the same shared commit and own only their platform-native visual acceptance. Neither platform task may independently restyle the shared rail.

The rail change lands as an independent commit before any startup optimization. A startup experiment that misses its performance gate cannot block or rewrite the accepted rail correction.

## Acceptance criteria

1. The released rail is visibly on the left side of the conversation text on both platforms.
2. Opening and closing a preview does not move, resize, or rewrap transcript text.
3. The preview never overlaps the composer band at 100%, 150%, or 200% scale.
4. Complete-history navigation, loading older Turns, current-mark following, keyboard focus, and reduced motion do not regress.
5. When the right Workbench leaves the center column below 680px, the rail may hide; closing or widening the Workbench restores it without rewriting the user's panel-width preference.

## Rollback

The visual commit can be reverted without changing Turn data, session files, pagination, BrowserSkill, or startup code. A rollback restores only the released 0.5.3 right-side placement.
