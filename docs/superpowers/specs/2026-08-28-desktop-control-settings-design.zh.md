# Desktop 浏览器与电脑控制设置设计

[English](2026-08-28-desktop-control-settings-design.md) | 中文

## 目标

将完整的**浏览器与电脑控制**设置模块重做为紧凑、清晰的列表，同时修复现有状态模型：当前原生电脑状态不可用时，会把两项能力一起标成不可用。新模块必须分别表达能力是否存在、用户是否开启、macOS 是否授予所需权限，以及最近一次刷新是否成功。

## 范围

- 只重做浏览器与电脑控制设置模块及其控制中胶囊；其他设置区域保持现有布局。
- 浏览器控制与电脑控制分别判断可用性，也分别由用户开启。
- 所有授权判断继续由 Electron main 持有。Renderer 只接收展示状态并发送封闭的设置意图；会话、租约、引用、坐标、批准令牌和原生身份不会向 Renderer 暴露。
- 开启任一能力、添加授权应用或修改紧急停止快捷键前，继续要求原生确认。
- 优先完成 macOS 0.4.3；本次不增加或改变 Windows 原生行为。

## 状态模型

移除单一汇总字段 `supported`，改为明确的能力状态和刷新状态：

- `browser.availability` 与 `computer.availability` 为 `available`、`unavailable` 或 `unknown`。生产 Adapter 已安装且有效状态明确支持时为可用；Adapter 不存在或明确不支持时为不可用；首次状态读取失败时为未知，而不是不可用。
- `browser.enabled` 与 `computer.enabled` 表示已持久化的用户策略。能力可用但尚未开启时必须显示为**可用 · 未开启**，绝不能显示**不可用**。
- `permissions.screenViewing` 与 `permissions.assistiveControl` 继续分别表示 macOS 的 `granted`、`denied` 或 `unknown` 状态。
- `refresh.status` 与 `refresh.apps` 分别使用封闭联合 `ready | checking | { failed, message }`。失败分支只提供长度受限的通用错误和重试意图，不暴露原生错误、路径、会话或页面内容。

电脑状态与应用枚举独立完成。应用列表失败时保留最近一次有效列表，不改变电脑控制的可用状态或权限。状态查询失败时，在 Authority 生命周期内保留最近一次有效原生状态，只把 `refresh.status` 标记为失败并提供重试；如果此前从未获得有效状态，则只把电脑控制标为未知，并把权限显示为未知。浏览器控制仍只由自身 Adapter 状态决定。

Electron main Authority 生成冻结且经过严格校验的快照。Preload 与 Client Validator 拒绝未知字段、自定义原型、可强制转换的值，以及任何携带授权能力的扩展字段。

## 模块布局

已确认的紧凑列表按以下顺序组成：

1. **标题区**——标题、一行说明，以及类似**2 项能力可用**的摘要。刷新失败时增加小型行内重试操作，但不覆盖仍然有效的能力状态。
2. **能力列表**——浏览器控制与电脑控制各占一行。每行包含图标、名称、简短说明、可用状态、开启状态和开关。只有该能力确实不支持、该项设置正在提交，或停止过程使扩展权限不安全时，才禁用对应开关。
3. **macOS 权限**——屏幕查看和辅助控制两个紧凑状态行。仅在权限被拒绝或未知时显示引导，并明确 Harness 绝不会自动修改系统权限。
4. **授权应用**——现有普通应用白名单。空列表、刷新失败和已加载列表必须在视觉上可区分；修改应用授权仍需原生确认。
5. **紧急停止**——已配置的快捷键及编辑控件。只要控制正在执行或清理尚未结束，停止操作始终无需批准且保持可用。
6. **当前控制**——无控制时显示空闲；有控制时显示 Agent、应用、当前动作和醒目的停止按钮。现有全局胶囊继续展示同一份权威状态的紧凑投影。

所有行使用现有 Desktop 的颜色、排版、边框和焦点 Token。状态不能只依赖颜色，必须同时使用文字和图标表达。窄屏下，状态信息与控件换行到标签下方，不产生横向滚动。键盘焦点顺序与视觉顺序一致；开关和按钮保留清晰焦点与可理解的无障碍名称。

## 数据流与设置修改

`ComputerControlUiAuthority` 分别读取三个来源：Coordinator Adapter 可用性、原生电脑状态和原生应用枚举。它只在内存中缓存最近一次通过校验的展示快照；设置仍由 `ControlSettingsStore` 持有。

Preload Bridge 保持现有零授权能力的形式。Renderer Bridge Operation 仍是浏览器开启、电脑开启、应用白名单、紧急快捷键、停止和重试组成的封闭集合。重试只触发 main 持有的新一轮状态与列表读取，不携带目标或会话数据。

所有设置修改串行执行。UI 只把受影响控件显示为提交中，忽略重复提交，并以 main 返回的权威快照替换状态。原生确认被拒绝或写入失败时恢复旧值并显示长度受限的行内错误，不做乐观持久化。

## 授权诊断

电脑控制包含三项独立判断：macOS 权限、持久化的电脑控制开关与应用白名单，以及短期有效的 Electron 原生任务租约。Harness 普通工具的 `ask` 或 `never` 审批策略不会授予、压制或持久化该桌面租约。设置模块会在应用列表旁明确说明这一区别。

Wire 错误清单使用安全原因 `CONTROL_DISABLED`、`TARGET_NOT_AUTHORIZED` 和 `APPROVAL_DENIED`。Electron 只在自身持有的判断点返回这些错误：电脑控制未开启或请求应用均不在白名单时，在原生批准之前返回；原生询问被取消时，在询问之后返回。`PERMISSION_DENIED` 继续表示操作系统权限结果；`POLICY_DENIED` 只表示敏感或其他受保护目标。工具将每个错误码映射为长度受限的纠正指引，绝不暴露 Helper 原始文字、应用标识、窗口标题或批准材料。

电脑控制可用且已开启、但尚未允许任何应用时，应用区域会醒目显示**请至少选择一个应用**。枚举到应用不代表已授权。选择应用仍需现有 main 进程持有的设置确认；下一次任务级操作随后打开独立的 **Allow Desktop control?** 询问。应用白名单会持久化，而任务租约会在 Turn 完成、停止、Session 或生命周期清理、空闲 5 分钟或总计 20 分钟时过期。

## 失败行为

- Provider 不存在或 Adapter 明确不支持时，只把对应能力标为不可用。
- 电脑控制关闭、有效应用白名单为空、原生批准取消、操作系统权限缺失和目标受保护时，分别显示不同的安全诊断。
- 状态超时、枚举失败、响应格式错误或 IPC 快照被拒绝时，必须失败关闭并显示可重试错误，同时保留其他不相关的有效状态。
- 停止保持幂等。清理期间禁止开启能力或扩大应用白名单；清理失败时继续显示停止区域和可重试错误。
- Renderer 或模型可见消息不得包含 Helper 原始 stderr、窗口标题、页面正文、绝对路径、租约标识、引用或批准材料。

## 验收

- 类型与 Validator 测试拒绝旧的汇总状态，以及所有未知字段、带原型字段、可强制转换字段和携带授权能力的字段。
- Authority 测试证明浏览器控制的可用性不依赖原生电脑状态；能力可用但未开启时显示为可用且未开启。
- 失败测试分别覆盖状态失败、列表失败、保留最近有效状态、首次加载失败、重试、设置拒绝和停止清理失败。
- 组件测试覆盖完整紧凑模块、所有能力组合、各权限状态、空列表与已加载应用、设置提交中、控制进行中、停止、窄屏布局、键盘操作，以及不依赖颜色的可见状态文字。
- Protocol、Coordinator、Provider 与工具测试证明三种安全授权错误能通过持有的 IPC 路径；空白名单不会打开原生询问；允许应用后会打开询问；Harness 普通 `ask` 或 `never` 策略不会参与该流程。
- 聚焦 macOS 验收从未允许任何应用开始，在不打开原生询问时观察纠正提示；随后在设置模块允许 Chrome、批准下一次任务询问，并针对新快照状态完成 `computer_snapshot`、`computer_focus` 和一次无害的 `computer_click`。
- macOS 打包验收使用隔离设置目录启动，证明两个已安装 Adapter 均显示可用，同时两个默认开关均显示未开启；随后在原生确认后分别开启，并验证刷新后不会出现汇总式不可用状态。
- 现有 Coordinator、Preload、菜单与托盘停止、Helper、浏览器控制、电脑控制、设置持久化及翻译配对测试继续通过。
