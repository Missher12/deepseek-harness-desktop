# Desktop 0.5.4 启动加速设计

[English](2026-09-04-desktop-0.5.4-startup-acceleration-design.md) | 中文

**状态：** 用户已于 2026-09-04 批准推荐方向；书面规格待复核

**Desktop 基线：** `0da8093092c9a29f5cebdfc094d0b58d97b56219`（公开 `desktop-v0.5.3`）

**Harness core 基线：** `0.1.2-alpha.5`

**目标 Desktop 版本：** `0.5.4`

## 目标

通过优化实测 Loader 关键路径，缩短从应用启动到真实可交互 Desktop surface 的时间，同时保持 readiness、profile 校验、授权、升级恢复与失败传播不变。

## 实测基线

最终 0.5.3 Windows 同 runner 证据把固定的 0.5.1 安装器与 0.5.3 候选放在同一 runner 上比较，每个产品分别采集五次冷启动和五次热启动。

| 指标 | 0.5.1 | 0.5.3 | 结论 |
|---|---:|---:|---|
| 冷启动 median | 4866ms | 6834ms | 需要调查的退化 |
| 冷启动 P95 | 6389ms | 7455ms | 需要调查的退化 |
| 热启动 median | 3486ms | 5931ms | 需要调查的退化 |
| 热启动 P95 | 3535ms | 6185ms | 需要调查的退化 |
| 0.5.3 冷启动 `profile-compose → loader-mount` | — | 2513ms | 主要有界子进程阶段 |
| 0.5.3 热启动 `profile-compose → loader-mount` | — | 2613ms | 主要有界子进程阶段 |

这些样本中的 `loader-mount → loader-settle` 只有数十到一两百毫秒，子进程报告 URL 后的 URL readiness 也很短。因此首要优化目标是 root include 创建与激活内部的工作，不是提前发出 readiness 信号，也不是移除 module fallback 安全校验。

这组五样本数据用于定位调查目标，但不构成 0.5.4 发布 benchmark（基准测试）。发布决定使用下述更大样本约定。

## 测量约定

- 现有固定 Desktop 里程碑和子进程计时行继续不包含路径、配置和凭据。
- 新增固定内部标记，分开 Loader 构建、root include 开始、第一方模块解析与导入、root 激活、settle 和激活审计。
- 只有明确第一方包白名单可以记录详细名称。用户安装包只报告汇总数量、总时长和最大时长，不报告包名、路径、配置或参数。
- 每个耗时都是非负安全整数。未知、畸形、重复或顺序不可能的证据作为 benchmark 证据快速失败，但不会把健康的产品启动变成产品失败。
- 普通 CLI 启动不输出启动计时。只有精确 Desktop 诊断环境才启用计时通道。
- 可移植 CI 产物只包含摘要和有界白名单计时记录，不包含生命周期日志、CPU profile、`DSH_HOME`、URL、路径、提示词、环境变量值或凭据。

## 优化阶梯

实现按实测影响推进，并在第一个满足发布门禁的安全改动处停止。

1. 删除同一次启动中针对相同不可变输入重复执行的第一方文件读取、YAML 解析、模块解析或组合工作。
2. 只有在会话恢复、路由、授权、Client manifest、首屏会话渲染与失败报告都不依赖它时，才把实测非关键第一方扩展移出启动关键路径。
3. 如果重复的不可变工作仍占主导，则增加可重建缓存，缓存键包含精确 Desktop/core 版本、平台、架构、package lock、内置 profile、bundle、patch 与模块内容摘要。
4. 遇到缓存 miss、损坏、版本不符、摘要不符或不支持的输入时，通过普通路径重新计算。绝不删除或重写用户 profile、patch、会话、记忆与进化数据、浏览器状态或凭据。

用户拥有的 profile 与 overlay 文件每次启动仍重新读取并校验。物理模块根、包边界、升级恢复与产品错误继续快速失败。本设计不序列化实时 Cordis context，不跨进程复用活动服务，不在没有顺序证明时并行激活带副作用的插件，也不跳过任何 Loader generation。

## Readiness 与用户体验

- `dsh web:` 继续只由真实 web 运行时在现有位置输出。
- `harness-ready` 继续要求真实 readiness 路由与 boot manifest。
- `desktop-running` 继续要求真实 Desktop surface，而不是加载窗口。
- 在实测子进程路径运行期间，加载窗口必须继续及时显示并保持响应。
- BrowserSkill 在启用或调用前保持休眠，不得给冷启动增加浏览器探测或 daemon。

## 测试与证据

1. 计时解析器测试拒绝畸形、重复、未知和链内逆序记录，同时接受独立链之间的合法交错。
2. 选定的优化先用聚焦 RED 测试复现重复或不必要的急切工作，再做最小 GREEN 改动。
3. 如果选择缓存，缓存测试覆盖精确命中，以及版本、lock、patch、bundle、模块、平台、架构、截断、篡改和外来文件失效。
4. 正确性回归覆盖 profile boot、Loader 失败传播、旧 fallback 恢复、会话恢复、授权、路由、BrowserSkill 休眠和进程树关闭。
5. 每个平台在同一 runner 上用十次冷启动和十次热启动比较固定的公开 0.5.3 产品与同一个 0.5.4 最终 SHA。
6. 报告包含总启动及每个固定阶段的 median 与 P95，并区分改善、退化和普通运行波动。

## 性能门禁

- 冷启动或热启动总时长 median 至少一项改善 15%。
- 另一项总时长 median 退化不超过 5%。
- 两项总时长 P95 都不得退化超过 10%。
- 正确性、readiness、原生生命周期与用户数据保留门禁全部保持 GREEN。
- 如果产品优化未达到任何一个门槛，则回滚该优化，只保留安全诊断改进。不得发布未证实的快速路径，也不得宣称启动更快。

## 所有权与交付

总指挥独占共享计时与启动实现。Mac 执行任务拥有 Intel macOS 基线和候选原生测量。Windows 执行任务拥有 Windows x64 基线和候选原生测量。平台任务消费同一个共享提交，只能修改各自的平台测量或生命周期脚本。

启动工作在独立的左侧导航轨修正之后落地。最终版本号、发布元数据、tag 与公开产物等待同一个最终 SHA 通过两个原生平台。

## 验收标准

1. 阶段级报告说明实测删除或延迟了哪些工作，且不包含用户私有数据。
2. Mac Intel 与 Windows x64 的同机十次冷启动和十次热启动比较都满足性能门禁。
3. 启动不会早于真实对应状态报告 URL、Harness readiness 或 Desktop readiness。
4. 现有 profile、会话、记忆与进化数据、授权状态和 BrowserSkill 状态在升级、启动、退出与卸载期间保持完整。
5. 如果存在缓存，失效或无效缓存回退到普通校验路径，不会让应用无法启动。

## 回滚

计时新增与产品优化使用独立提交。可以回滚优化并保留诊断证据。如果存在缓存，它必须可重建、可移除；回滚绝不触碰用户拥有的数据。
