# Desktop 0.4.3 Browser Control, Computer Use, and Prompt Rail Design

English | [中文](2026-08-27-desktop-0.4.3-computer-use-design.zh.md)

## Goal

Starting from revised Desktop 0.4.2 commit `5998cfbe523f98809c6170a5d67bce499e684728`, ship one-source Mac Intel and Windows x64 Desktop 0.4.3. The release adds two observable and revocable Agent capabilities: structured control of the built-in browser and user-authorized control of multiple local applications. It also updates prompt navigation to the user-approved, high-visibility Codex-style rail.

The feature must not expose the Electron renderer, arbitrary JavaScript, a remote-debugging port, AppleScript, PowerShell, or unconstrained pointer/keyboard APIs to the model. Existing Harness approval, session ownership, tool lifecycle, and application cleanup remain authoritative.

## Scope

- Browser Control: navigation, semantic page snapshots, optional screenshots, referenced-element clicks, text input, keys, selection, scrolling, waits, back, forward, reload, and stop.
- Computer Use: enumerate grantable apps/windows, focus an app, return accessibility snapshots and optional window screenshots, click, double-click, drag, type, press keys/chords, scroll, and wait.
- Multi-app control through a user-managed application allowlist; one task may move between multiple authorized apps.
- One approval per task through a short-lived `ControlLease`; sensitive actions remain individually approved or denied.
- Visible takeover state with app, window, session, status, and Stop controls plus a global emergency shortcut.
- Prompt rail navigation only, with no edit, rewind, delete, fork, draft restore, or automatic-send semantics.
- The same 0.4.3 source supports macOS and Windows through distinct native adapters, never shell-script parity theater.

## Non-goals

- Rewriting Harness, Electron, or the existing tool system.
- Duplicating Bash, PowerShell, Terminal, Jobs, Workflow, filesystem tools, or the sandbox.
- Reading passwords, one-time codes, payment-card data, keychain content, or OS security credentials.
- Automatically approving payments, publishing, sending, installation, removal, destructive deletion, trash emptying, or OS permission changes.
- Silent background control or a plugin bypass around the control indicator and stop mechanism.
- Arbitrary script injection, CSS/XPath selectors, IPC payloads, process injection, or raw operating-system APIs in the first release.

## Chosen Approach

### Adopted: two capability seams with native adapters

Add independent `browserControl` and `computerControl` Service Definitions, Host adapters, and model-facing tool Consumers. The Harness child and Electron main process communicate over a dedicated, strongly typed IPC with a closed action vocabulary. The browser adapter reuses the built-in `WebContentsView`; the desktop adapter forwards bounded actions to an on-demand native helper.

The macOS helper uses AXUIElement for app, window, and control semantics; ScreenCaptureKit or CoreGraphics for authorized-window capture; and CGEvent for the closed action set. The Windows helper uses UI Automation for the semantic tree, Windows Graphics Capture for authorized-window capture, and SendInput for the closed action set. Rust is appropriate for this native helper to provide stable native types, process isolation, and a shared protocol; this is not a rewrite of Harness in Rust.

### Rejected: a separate Playwright browser

A Playwright Bundle is straightforward to isolate, but duplicates Chromium, increases package size and memory, and cannot naturally control the built-in browser page the user is viewing or already signed into. It may remain a test dependency, not the product path.

### Rejected: shell, AppleScript, or PowerShell automation

Script automation is quick to prototype but unreliable for element identity, window ownership, scaling, cancellation, auditing, and platform parity. It also risks bypassing Harness approval. Scripts remain ordinary user-invoked commands and are not a Computer Use backend.

## Browser Control Architecture

The Agent receives an ephemeral per-session browser partition by default and does not inherit user login cookies. A user may press **Give to Agent** in the built-in browser to grant the current visible page to the current session. The grant conveys control of that BrowserView only; it never exports cookies, local storage, or credentials.

Each `browser_snapshot` returns the URL, title, navigation revision, a bounded semantic tree of interactive elements, and a screenshot attachment only when a vision-capable model requests one. Element references are opaque and tied to the navigation revision; navigation, a material DOM change, or closing the page invalidates them. Click and type actions accept only current refs, never model-supplied JavaScript, selectors, or coordinate strings. Coordinate clicks are a visual fallback tied to the screenshot revision and visible BrowserView bounds.

Page content is always untrusted. Page text cannot grant permissions, expand allowlists, approve sensitive actions, or instruct Harness to bypass policy. Popups, downloads, camera, microphone, location, clipboard reads, and new windows are denied by default. Uploads accept only a short-lived file handle selected explicitly through the native picker.

## Computer Use Architecture

`computer_snapshot` binds to one authorized application and window, returning its accessibility tree and an optional screenshot. Semantic refs bind the process, window, snapshot revision, and display scale; a changed window makes old refs fail closed. The Agent prefers semantic refs. Coordinate actions are available only when no usable accessibility element exists and the selected model supports image input.

The native helper accepts only `list`, `focus`, `snapshot`, `click`, `doubleClick`, `drag`, `type`, `key`, `scroll`, `wait`, and `stop`. Every request includes the session, lease, app, window, revision, action limit, and deadline. It accepts no shell, script, dynamic-library path, environment override, or generic IPC payload. Parent disconnect, app exit, session end, or lease revocation immediately releases input state and terminates the helper.

Models without image input are limited to DOM or accessibility semantics and cannot guess screen coordinates. Screenshots go through the existing Harness attachment service as ImageBlocks, never as unbounded base64 in IPC or logs.

## Authorization and Safety

Settings expose separate Screen Viewing and Assistive Control states. Missing permission produces a clear local status and a manual path to system settings; Harness does not loop prompts or modify system settings automatically.

One user approval creates a short-lived `ControlLease` bound to the session, allowed apps, windows, capabilities, and maximum lifetime. It expires at task completion, session switch, app restart, human takeover, five idle minutes, or a twenty-minute hard limit. Settings can revoke one app or all grants.

A normal lease cannot silently authorize password or secure-text fields, one-time codes, biometrics, keychains/password managers, OS privacy/security settings, payments/orders, external send/publish actions, installation/removal, destructive deletion, or downloading and executing a file. Reliably identified credential entry is denied; other high-impact actions require a final prompt showing the action, application, control name, and effect.

Control always displays a top status pill with the Agent, current app, action state, Pause, and Stop. The menu bar or tray mirrors Stop. The default global emergency shortcut is `CommandOrControl+Shift+F12` and is configurable. Stop revokes the lease, clears queued actions, releases input state, and records a local audit event without screen content.

## Prompt Rail

Use the user-approved first visual: a 28–32 px gutter at the left of the transcript with no panel or card timeline. Ordinary prompts use visible but restrained neutral-gray ticks. The active prompt uses a longer DeepSeek-blue tick with a hollow dot. Hover or keyboard focus displays “Prompt N · time,” up to two preview lines, and the current/total count.

The current ordinary tick references an undefined `--dsw-alias-label-quaternary`; replace it with a defined theme token plus fallback. The guide and ticks must remain visible in light, dark, non-Retina, and forced-colors modes. Long histories must not stack 120 overlapping button hitboxes: the rail maps pointer Y to the nearest anchor, while keyboard interaction uses roving tabindex, arrows, Home, and End. Narrow layouts collapse into a small Prompt Navigation button instead of silently removing the feature.

Clicking reads only the required history and scrolls to the exact user prompt, with a short theme-colored location highlight. It never edits history, creates a session, restores a draft, rewinds, deletes, or sends.

## Performance and Privacy

- The native helper starts on demand and exits when idle. With no control task, it performs no capture, accessibility polling, or high-frequency timer work.
- Browser tools prefer semantic diffs. Desktop captures are window-cropped and downsampled to model needs. Active control is capped at 2 FPS and idle capture is 0 FPS.
- Screenshots and semantic snapshots stay in bounded current-session attachments/tool results and never enter telemetry, ordinary logs, memory, or MSE candidates.
- Password values, cookies, local storage, authorization tokens, and hidden-window content are never returned to the model.
- A changed target returns `STALE_REF`; the Agent must snapshot again instead of blindly replaying coordinates.
- Actions per turn, snapshot bytes, semantic nodes, text length, and total lease time all have hard limits.

## UI and Error Handling

Settings add a Browser & Computer Control section matching existing setting cards. It reports platform support, OS permissions, authorized apps, default sharing mode, emergency shortcut, and the last local control state. The marketplace reports the Desktop-owned capability as loaded rather than permanently saying “restart to load.”

The built-in browser gains **Give to Agent / Stop takeover**. An ephemeral Agent browser opens visibly in the workbench. Sharing the current page shows a signed-in-state warning. Computer Use does not steal focus at startup; the first interactive action activates the target app.

Missing permission, closed windows, exited apps, occlusion, capture failures, unavailable accessibility trees, stale refs, non-vision models, and user stops return structured errors. They must not prevent Harness startup, block ordinary chat, or leave a helper, held key, active drag, or BrowserView behind.

## Tests and Acceptance

- Contract tests cover schemas, size bounds, stale refs, foreign sessions, expired leases, invalid actions, and unknown fields, all failing closed.
- Browser tests cover isolated partitions, explicit sharing, semantic snapshots, click/type/scroll/wait, invalidation, popup/download/permission denial, handle-based upload, and hostile page text that cannot authorize.
- Computer tests cover app/window identity, display scaling, semantic refs, coordinate fallback, input release, user stop, helper crashes, and parent disconnects.
- Sensitive tests prove secure text, codes, payments, sends, installs, deletion, and system settings cannot execute silently under a normal lease.
- Model tests prove vision models receive bounded images, while text models receive DOM/AX text only and cannot call coordinate actions.
- Rail tests cover valid theme tokens, light/dark/forced-colors snapshots, dense nearest-anchor hit testing, keyboard navigation, narrow-layout access, exact history reveal, and no side effects.
- Performance tests prove 0 FPS idle, on-demand helper startup, capture throttling, long-task memory bounds, and no surviving process after exit.
- Product regression covers chat, plugins, memory, MSE, system update, workbench, shell/terminal/jobs, and preservation of `~/.dsh`.
- Native acceptance from one source commit covers installation, permission onboarding, a controlled browser task, a controlled multi-app task, sensitive-action denial, emergency stop, app exit, process cleanup, uninstall, and data preservation on Intel Mac and Windows x64.

## Release Gates

0.4.3 cannot claim Computer Use merely because it launches an app. Release evidence must show a visible multi-step browser task and, on each platform, observation, clicking, typing, and stopping across at least two harmless test applications, with denial branches producing no side effects.

The current unsigned/unnotarized macOS build cannot guarantee that TCC permissions survive replacement installs. A clearly labeled test release is possible without a Developer ID, but it must not claim durable permissions; the recommended production release requires stable signing, notarization, permission descriptions, and upgrade identity. Windows must likewise disclose SmartScreen/code-signing status.

Every build comes from the final shared commit and a fresh `desktop-v0.4.3` tag. Public assets must be verified for uploaded state, size, SHA-256, checksum files, and one anonymous re-download. They must contain no keys, cookies, screenshots, user files, `~/.dsh` data, or local permission databases.
