# 内置 Agent 预设扩展设计

[English](2026-08-20-agent-presets-expansion-design.md) | 中文

## 状态与已确认决定

DeepSeek Harness 保留现有四个随附预设及其稳定 id：`standard`、`code`、`minimal` 与 `cordis`。本次变更新增八个随附预设。用户通过现有的新会话选择器手动选择每个预设；不增加需求分类器、自动路由或会话中途模式切换。

第一阶段只面向内部 Intel macOS 应用，不发布 GitHub Release，也不宣称完成 Windows 验收。

## 目标

让 Agent 预设选择器同时覆盖工作阶段和技术岗位。选中预设后应真正改变 Agent 处理任务的方式，而不只是改变设置页展示的名称。因此每个新预设拥有不同的角色契约，同时保留 Harness 已经成熟的文件检查、本地开发、计划、测试、Skills 与受控委派组装。

## 现有基线

当前随附名单包含：

| Id | 展示名称 | 用途 |
|---|---|---|
| `standard` | 标准模式 | 功能完整的通用编码 Agent |
| `code` | PTC 模式 | 通过 Code Mode 呈现标准模式能力 |
| `minimal` | 极简模式 | 只提供持久 Bash 与字符串替换编辑 |
| `cordis` | 创造模式 | 创作和实验 Agent 预设与 Cordis 组装 |

这些 id 继续存在并保持行为。已有会话头部可能引用它们，而且会话一旦产出内容，其预设便被锁定。重命名或删除这些 id 会制造没有必要的兼容风险。

## 备选方案

### 只增加名称和提示词

这是改动最小的方案，但会产生看起来不同、实际工作行为几乎相同的预设，也无法提供字符串断言之外的可靠回归面。本方案不采用。

### 八个独立随附组装

每个新预设都是普通随附预设目录，拥有自己的 `preset.yml` 与 `agent.cordis.yml`。它遵循仓库现有的快照模型：组装从已知良好的标准能力集开始，再携带一份简洁、接近 Codex 的共同工作契约与角色专属契约。发现、展示、手动选择、会话锁定和损坏预设报告无需新增 API 即可继续工作。这是选定方案。

### 自动路由或预设继承

自动路由必须在会话变为非空前分类第一条需求，而且可能误选。组装继承需要引入当前预设域刻意没有提供的新运行时格式和生命周期规则。两者都超出了这次“手动选择并安装预设”的范围，暂缓处理。

## 新增随附名单

| Id | 展示名称 | 主要行为 |
|---|---|---|
| `planner` | 方案规划 | 澄清目标、检查证据、比较方案，并在实现前交付可执行计划 |
| `frontend` | 前端与 UI | 构建精致界面，覆盖响应式几何、无障碍、交互状态和视觉验证 |
| `backend` | 后端与 API | 处理 API、数据模型、持久化、兼容性、安全边界和聚焦的集成测试 |
| `debugger` | 故障排查 | 先复现、隔离根因、区分证据与推断，再执行最小且获授权的修复 |
| `reviewer` | 代码审查 | 从正确性、回归、安全和缺失测试角度审查差异与行为，按严重性报告问题 |
| `qa` | 测试与 QA | 设计基于风险的测试、复现用户流程、记录证据，并区分环境失败与产品缺陷 |
| `devops` | DevOps 与发布 | 负责本地构建、打包、CI、部署预检、回滚规划和产物验证 |
| `research` | 文档与研究 | 阅读代码和资料、综合结论、维护精确文档，并明确标注不确定性 |

展示顺序保持确定：现有四个预设继续位于 1–4，新预设按上表顺序使用 5–12。

## 共同的 Codex 风格工作契约

每个新角色都采用相同的简洁工程纪律：

1. 修改文件前，先理解目标、仓库指令、当前行为和受影响的数据流。
2. 面对非简单工作时先形成简短的内部计划，并把改动限制在用户要求的范围内。
3. 证据优先于假设，保留无关的工作区改动，并避免破坏性操作。
4. 按风险程度验证，没有观察到的结果绝不宣称已经完成。
5. 清楚报告结果、修改范围、测试和剩余限制。

角色专属文字接在共同契约之后，改变工作重点、执行顺序和修改策略。它必须足够简洁，避免切换预设后产生过高的重复提示词成本。

## 角色边界

`planner` 和 `reviewer` 默认只分析。`debugger` 先诊断后修复，而且只有用户要求修复时才编辑。`qa` 可在用户要求时创建或更新测试资产，但不会在只需报告的任务中悄悄修改产品代码。开发类角色可以编辑和测试本地代码。`devops` 可以构建和执行本地预检，但生产写入、公开发布、凭据使用和破坏性操作仍需明确授权。

这些行为是 Agent 契约，不是安全边界。当前文件系统插件同时发布 read、write 和 edit，Shell 工具同样可以改变状态。真正的强制边界仍由 Harness 权限预设、沙箱策略、审批流程和用户授权负责。界面和文档不得把提示词约束的角色称为技术上无法写入的“只读模式”。

## 架构与文件

每个新内置预设位于：

```text
packages/preset/agent-presets/presets/<id>/preset.yml
packages/preset/agent-presets/presets/<id>/agent.cordis.yml
```

`preset.yml` 只包含随附展示元数据和数字顺序。`agent.cordis.yml` 是自包含组装，与当前“不继承”的设计保持一致。不新增持久化 schema、网关方法、preload bridge 或 React 组件。现有名单自动发现这些目录，当前设置卡片展示它们，当前新会话 chip 应用用户的手动选择。

除非某个角色有明确理由省略，新组装保留标准模式稳定的本地开发服务。角色差异主要放在 persona 契约中；只有确实能改善模型表面时才移除工具，并且不会把工具移除表述成安全保障。目录回归测试记录每个预设预期的插件 id，防止以后修改 `standard` 时让八份快照悄悄落后。

## 数据流

1. Desktop staging 把随附预设根目录复制进打包后的应用。
2. Agent 预设名单发现全部十二个目录并读取元数据。
3. 设置页与新会话 chip 渲染现有的有序名单。
4. 用户为下一个会话手动选择一个预设。
5. 会话产出内容之前，宿主组装该预设，并把 id 记录进持久会话状态。
6. 会话在整个生命周期内保持该组装；修改默认值只影响之后的新会话。

没有自动分类器读取用户需求，也不会迁移现有对话。

## 失败处理

继续以现有发现与挂载行为为准。格式错误的新组装显示为损坏的内置预设，且无法选择。挂载失败会回滚这次会话组装尝试，而不会移除之前的常驻预设。即使一个新角色无效，原有四个仍能被独立发现。

如果缺少预期目录、元数据文件、组装文件、唯一 id 或唯一顺序，打包构建必须在预设目录测试中失败。安装沿用现有可恢复 Desktop 流程：关闭运行中的应用、保留带时间戳的备份、替换应用、比较打包字节并从安装路径启动。

## 验证

源码测试覆盖：

- 精确发现四个现有 id 与八个新增 id；
- id、名称和确定顺序均唯一；
- 每个新组装都能成功解析和挂载；
- 共同工作契约与各角色的区别指令；
- 八份快照各自预期的插件目录；
- 空白会话手动选择，以及产出内容后的锁定；
- 保留四个现有预设及其行为；
- Desktop staging 包含每个新增预设目录。

UI 测试验证现有选择器和管理卡片可以显示十二个角色，且不会增加自动路由控件。打包后的 Intel macOS 冒烟测试打开真实应用，为空白会话选择至少一个新预设，并确认创建的会话报告该 id。只有类型检查、Lint、聚焦测试、Desktop 打包和原生冒烟验证全部通过后，才安装最终内部构建。

## 验收标准

1. 现有四个预设 id 继续可用且保持不变。
2. 八个新内置预设出现在现有手动选择器和设置管理分区。
3. 用户可以为新会话手动选择任意新预设，不出现自动推荐或自动路由。
4. 每个新预设拥有不同角色契约，并通过组装验证。
5. 现有会话、设置、凭据、用户自建预设和聊天数据保持完整。
6. 最终 Intel macOS 应用完成备份，安装到 `/Applications/DeepSeek Harness.app`，启动并从该确切路径验证。

## 范围之外

自动需求分类、会话中途切换预设、新权限引擎、技术上强制只读、组装继承、新预设编辑器、删除或重命名现有四个预设、Windows 打包、GitHub 发布和公开 Release 产物不在本次范围内。
