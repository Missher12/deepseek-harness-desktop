# Desktop 0.4.1 Layout and Startup Design

English | [中文](2026-08-26-desktop-0.4.1-layout-startup-design.zh.md)

## Goal

Ship one Mac Intel and Windows x64 Desktop 0.4.1 source revision that fixes the reasoning popup layout with large model catalogs and improves measurable Desktop startup latency without changing provider capability discovery, model request semantics, user profiles, or Harness data.

## Scope

- Keep the existing six-stop reasoning ladder, adaptive above/below portal placement, model selection, and character-slider preference.
- Make the popup a three-region layout: non-scrolling effort header, independently scrolling model catalog, and non-shrinking character-slider footer.
- Measure startup milestones locally and optimize only proven synchronous or duplicate work.
- Run Mac packaged acceptance and Windows native installer acceptance from the same commit.
- Defer every GitHub operation until local verification is complete, then use one synchronization, one push, and one release workflow.

NewAPI and other provider capability discovery changes are explicitly out of scope for 0.4.1.

## Reasoning Popup

The popup remains a fixed-position portal whose maximum height comes from the existing placement controller. The popup itself stops scrolling. Its children become:

1. `effortPane`: fixed-size slider or unsupported state.
2. `modelPane`: `flex: 1`, `min-height: 0`, `overflow-y: auto`; it owns all model and empty/loading content.
3. `preferenceFooter`: fixed-size footer with its own separator and menu background.

This preserves down-first placement and above/below flipping while preventing a large model catalog from pushing the character control into model rows. Focus order remains slider, model choices, footer. Keyboard escape, tab return, pointer dismissal, and reduced-motion behavior remain unchanged.

## Startup Optimization

Startup work is divided into measured milestones: Electron ready, window prerequisites ready, local loading page visible, module fallback ready, Harness URL reported, Harness page ready, and Desktop running. Diagnostics contain only durations and stage names.

Three bounded optimizations are permitted:

1. Read Desktop preferences and saved window bounds concurrently before creating the BrowserWindow.
2. Add an opt-in cached module-fallback healer for Desktop. Its cache is keyed by the installation anchor, Desktop version, and root manifest identity, stores only package names and resolved link targets, and verifies every cached link before taking the fast path. A missing, malformed, moved, or mismatched cache performs the existing full healer and rewrites the cache atomically. CLI behavior remains unchanged.
3. Coalesce duplicate reasoning model-directory loads while the same request is in flight, and avoid an immediate second refresh when opening the popup directly after its initial load. A later open still refreshes normally.

An optimization that does not improve the isolated startup benchmark or weakens recovery is not retained.

## Safety and Compatibility

- No reads from or writes to provider secrets are added.
- No profile bundles, external plugins, sessions, memories, or user configuration are removed or rewritten.
- The fallback cache is advisory. The verified filesystem links remain authoritative, and any mismatch falls back to the existing full repair.
- The popup changes only presentation and refresh coalescing; model IDs and reasoning efforts sent to Host are unchanged.
- Desktop 0.4.1 remains unsigned/unnotarized unless the existing release pipeline already supplies signing credentials.

## Verification

- Regression test with enough models to overflow the popup: only the model pane scrolls and the character control remains in the footer.
- Existing placement, pointer, touch, keyboard, preference, and model-selection suites stay green.
- Module-fallback cache tests cover hit, miss, malformed cache, moved installation, tampered/missing link, atomic rewrite, and Windows junction spelling.
- Lifecycle tests prove preference and window-state reads overlap.
- Load-coalescing tests prove one in-flight load and a later real refresh.
- Five isolated cold and five warm packaged Mac starts record median stage timings; 0.4.1 must not regress total startup and should improve the warm wrapper stage.
- Mac DMG packaged smoke and `hdiutil verify` pass.
- Windows Setup build, visible install, launch, close, uninstall, shortcut cleanup, and Harness data preservation pass from the same commit.
- Release assets are verified in CI so the local Mac does not repeatedly download large public artifacts.
