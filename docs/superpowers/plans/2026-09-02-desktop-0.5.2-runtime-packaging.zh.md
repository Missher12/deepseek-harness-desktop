# Desktop 0.5.2 启动、包体与 Windows 图标实施计划

[English](2026-09-02-desktop-0.5.2-runtime-packaging.md) | 中文

> **面向 agent 执行者：** 必须使用 superpowers:subagent-driven-development（推荐）或 superpowers:executing-plans 逐项实施本计划。步骤使用复选框（`- [ ]`）跟踪。

**目标：** 在不伪造 readiness、不破坏离线运行和 Profile module fallback 的前提下缩短冷启动、减少可证明冗余的 Windows 安装字节，并让 Windows 任务栏、托盘和安装器图标在小尺寸清晰。

**架构：** 先用同机 fixture 固化启动与包体基线，再增加无敏感信息的诊断证据；只保留有前后数据的优化。包体由 staged tree 清单约束；Windows 使用独立小尺寸图标资产，Mac 资产不变。

**技术栈：** TypeScript、Node.js、Electron 43、electron-builder、Vitest、PowerShell、Playwright packaged smoke、GitHub Actions。

**基线与所有者：** 基线由总指挥提供的完整 SHA 决定；Windows 执行任务是本计划共享启动/包体实现与 Windows 专属资产的唯一所有者。Mac 任务只能在收到共享提交后做 Mac 适配和原生复测。

### 任务 2：定位并优化真实 Harness 启动瓶颈

**文件：**

- 性能候选：只修改同机诊断识别出的最慢插件及其测试

- [ ] **步骤 1：编写 RED 测试。** Desktop 子进程只能输出固定 profile-compose、loader-mount、loader-settle、activation-audit 阶段与毫秒数；解析器不得接受路径、URL、插件配置或任意阶段名。
- [ ] **步骤 2：** 通过 Desktop 专用显式开关注入计时回调；普通 CLI 默认输出保持不变，`dsh web:` 仍只在 Loader 真正完成且必要路由存在后出现。
- [ ] **步骤 3：** 在临时 Home 对五次冷启动采样，并用 Node/V8 CPU profile 或等价只读证据确认耗时最大的同步 import/初始化；profile 文件只保留在 CI 临时目录，不上传含本机路径的原始文件。
- [ ] **步骤 4：编写瓶颈模块的 RED 性能/调用测试。** 只允许两类实现：把非首屏、非核心 API 的重初始化延迟到首次使用；或把同一次启动内完全相同的读取/导入合并为一个 Promise。审批、会话恢复、Client manifest、API 路由和失败传播不得延迟。
- [ ] **步骤 5：** 实施一个最小优化，运行该模块的功能/错误/取消测试与 Desktop readiness、failure、retry、process-tree 回归。
- [ ] **步骤 6：** 同 runner 重跑 5 冷 + 5 热；保留条件为冷启动 median 至少改善 15%，P95/热启动/失败恢复不退化。未达标则撤销产品优化但保留基准与诊断工具，并报告真实下限。
- [ ] **步骤 7：** 提交 `perf(desktop): reduce measured harness startup work`；提交说明附前后 summary，不附原始用户路径。
