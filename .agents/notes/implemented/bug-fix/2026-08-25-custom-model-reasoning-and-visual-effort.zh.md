# Agent Note: 自定义模型推理能力与视觉档位身份

Status: implemented

[English](2026-08-25-custom-model-reasoning-and-visual-effort.md) | 中文

## 问题

从「模型」页面创建的手工声明 pi-ai 模型只携带身份与容量，不带 `reasoningEfforts`。适配器因此会正确声明该模型没有推理能力，Desktop 推理控件随之不可用，而产品内又没有位置补充这项逐模型事实。

Desktop 的固定六档控件还会把超出模型真实上限的视觉档位映射到该上限，但收起后的触发按钮展示的是 Host 的真实档位名称。在仅支持 High 的模型上选择 Ultra 后，滑块会到达 Ultra 并提交 High，按钮却随即改回 High。虽然分发是安全的，界面选择却与用户手势矛盾。

## 决策

每条 pi-ai 模型行都在既有「模型详情」折叠区内提供推理能力选择器。「自动」会省略 `reasoningEfforts` 并保留已安装模型目录的声明；「不支持推理调节」写入 `false`；「仅 High」只写入 `{ high: "high" }`；Low 到 Max 的上限选项会显式写入直到所选上限的全部标准档位。该设置属于模型而非提供方，因为同一路由下的模型可能具有不同能力。手工声明模型在用户选择能力前继续采取保守行为。

Desktop 推理控件把视觉身份与提供方身份分开。只要 Host 仍报告映射后的真实档位，它就会在按 profile 保存的有界映射中，以确切会话／提供方／模型路由为键记住已接受的六档位置，并同时用于滑块和收起后的触发按钮。分发、持久模型选择和模型上限文案仍然只使用 Host 公布的真实档位 ID。因此在仅支持 High 的模型上选择 Ultra 后，界面可跨重挂载、会话切换、Desktop 随机端口和应用重启继续显示 Ultra，Host 收到并记录的则仍是 High。

## 验证

Client 测试会区分确切的仅 High 能力与 `low`／`medium`／`high` 上限、要求收起按钮保留 Ultra、通过鉴权后的 Host 偏好 seam 持久保存确切会话／模型视觉路由，并在控件重挂载后恢复 Ultra。HTTP 测试覆盖严格补丁形状、损坏读取和有界路由数据。真实 Models Web 组合会在浏览器中创建手工声明路由、选择逐模型能力、校验生成的设置文档，并快照重开的控件。Desktop 成品冒烟继续使用仅支持 High 的路由，选择 Ultra 后要求活动触发按钮显示 Ultra，而已存真实档位保持 High。

## 备选方案

**假定每个手工声明模型都支持所有推理档位。** 不采用，因为模型列表端点不会报告推理协议能力；静默发送不受支持的参数，会把配置便利变成提供方故障。

**增加一个提供方级推理开关。** 不采用，因为一个提供方可以服务不同上限的模型；路由级值要么夸大能力，要么会让更强模型的能力不可见。

**向提供方发送 `ultra` 或修改核心档位 ID。** 不采用，因为 Ultra 是 Desktop 的视觉档位，并非每个适配器都会公布的能力。核心继续按照[适配器持有能力的决策](../architecture/2026-07-24-adapter-owned-reasoning-effort-capabilities.zh.md)要求使用适配器持有的精确 ID。

**把 Ultra 重新标成映射后的真实值。** 不采用，因为这会让控件看起来撤销了用户的选择。独立的模型上限行已经能说明真实上限，无需改写选中的视觉档位。

## 影响

自定义模型获得一条显式且安全的推理滑块启用路径，不改变适配器默认值，也不凭空捏造能力。选择标准上限意味着端点接受直到该上限的每个标准档位；需要自定义协议值拼写的部署仍使用 `settings.yaml`，未触碰的隐藏映射会在普通模型编辑中保留。

视觉档位与真实档位可以有意不同。插件会在自己的本地 profile 分节内为最多 64 条确切会话／提供方／模型路由保留视觉选择，而持久化请求事实仍是映射后的 Host 档位。该映射不包含 prompt 或回复正文，复用插件既有的精确 capability 鉴权 loopback 端点，并在满额时淘汰最早路由。
