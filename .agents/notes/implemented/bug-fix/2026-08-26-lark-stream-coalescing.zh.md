# Agent Note: Lark 卡片流合并最新状态

Status: implemented

[English](2026-08-26-lark-stream-coalescing.md) | 中文

## 问题

Lark 卡片流会把每个 Harness 投影修订串行排在已配置节流间隔之后。模型输出即使已经在 Harness 中及时完成，飞书仍可能按分片数量乘以该间隔继续显示不完整内容；同时，产生的大量 `im.message.patch` 还会增加触发飞书限流的风险。

## 决策

每个 `TurnCardStream` 持有一个最新投影、一个可选节流计时器和一个可选在途卡片请求。中间修订会替换最新投影，并且不等待网络写入就返回。计时器触发前或请求在途期间收到的修订都会合并为最新状态。

终态修订会取消计时器并绕过节流。空闲时立即写入；已有一个请求在途时，只等待该请求。它的 promise 只会在最新最终状态完成写入或有界降级结束后结算。文字相同的修订仍可更新工具、审批、运行时事实、耗时和 token 用量；缩短文字仍会被拒绝。

第一次卡片更新失败后，不再执行后续卡片写入，并从最新投影尝试一次有界文本降级。插件清空活动轮次前，流停用会先取消自身计时器。调度器完全保留在 `@deepseek-ai/dsh-lark` 内；Harness 核心、Session 持久化、Desktop 会话渲染和 Desktop 默认 patch 均未改变。Lark 使用既有 `resolveOrdinaryTargetForSource()` API，因此 `@deepseek-ai/dsh-session-messenger` 不保留未使用的无来源解析器导出。

## 已考虑的替代方案

**缩短节流间隔。** 未采用，因为它仍会为每个模型分片发送一次 patch，只会提高限流压力，无法约束完成延迟。

**只渲染最终答案。** 未采用，因为这会移除用户要求的打字机进度，并延迟工具与审批可见性。

**把调度移入 Harness 核心。** 未采用，因为飞书 patch 节奏属于传输特定行为，而且可移除插件已经能够接收全部所需 Session 事件。

## 验证

确定性计时器测试要求突发修订只产生一次最新状态写入、终态修订最多只等待一个在途写入、停用取消待触发计时器、缩短文字继续被忽略，并且卡片失败最多只发送一次有界降级。现有卡片测试继续保留精确模型、提供方、推理档位、耗时、token、缓存、审批和文字单调断言。包测试、类型检查、Bundle 构建、文档门禁、Profile 安装、已安装字节对比、重启诊断和一次真实所有者私聊覆盖其余交付层。

## 影响

飞书写入次数由流持续时间约束，不再随分片数量增长，而且完成状态不会排在本地陈旧修订队列之后。很短的轮次可能只在占位卡之后显示最终卡片更新；较长轮次仍会按已配置间隔保留打字机进度。一个已经开始的飞书请求无法取消，因此终态修订仍可能等待这一个请求及其网络时延。
