# Agent Note: 并行执行安全的桌面启动工作

Status: implemented

[English](2026-08-18-overlapped-desktop-startup.md) | 中文

## 问题

Desktop 生命周期原本会先等待本地加载页完成，再开始只读的同目录运行时所有权检查；检查结束后才启动 Harness。这些彼此独立的等待被串行放进冷启动关键路径，而加载页本身既不读取也不写入 Harness 数据。

## 决策

Desktop 现在同时启动加载页 Promise 与所有权检查。只要发现已有写入者，仍然不会启动任何新运行时。检查确认安全后，所拥有的 Harness 会在加载页收尾期间开始启动；跳转到 Harness URL 仍然必须同时等待这两项工作，并通过原有的完整 Harness 就绪探测。

如果运行时已经开始启动后原生窗口创建失败，Desktop 会先停止自己拥有的运行时，再继续抛出窗口失败。运行时自身失败仍会进入原有的封闭启动失败页。

## 验证

生命周期测试会让加载页保持未完成，并证明所有权发现已经开始、Harness 在发现完成前仍被阻止，以及发现确认安全后 Harness 可以在加载页完成前启动。重建的 Intel 应用通过了完整隔离 macOS 成品冒烟，覆盖随机端口所有权、扩展 UI、跨会话消息、精确 Session ID 剪贴板操作、受保护文件逐字节一致与完整退出清理。

安装后的候选应用在自己拥有的随机回环端口返回 HTTP 200 与完整启动清单。由于测量期间有无关宿主进程占满 CPU，现场前后耗时没有被当作可比较证据。

## 备选方案

**在 Loader 树稳定前公布回环 URL。** 这样可能更早显示 Web 外壳，但同级插件仍可能在 URL 公布后失败。Desktop 继续保证完整就绪信号真实可靠。

**在 Desktop profile 中禁用普通 Harness 插件。** 这会通过删除产品能力减少工作量，也可能让 Desktop 行为偏离浏览器表层。本次优化保留相同组合。

## 影响

这项改动消除了可避免的编排串行等待，同时没有削弱写入者排除或启动真实性。Harness 插件树激活和约 5.5 MB 的初始 Client 脚本负载仍是更大的冷启动成本；若要继续明显缩短时间，需要单独的架构工作。
